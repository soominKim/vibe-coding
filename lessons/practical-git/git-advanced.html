코드 버전 관리하기 (Git & GitHub)

조금 더 공부하기

코드 버전 관리하기 (Git & GitHub) - 조금 더 공부하기

얻어갈 것

  • 커밋을 작게 쪼개는 습관이 왜 AI 작업의 안전장치가 되는지 이해합니다.
  • 사고가 났을 때 restore / reset / revert 중 어느 상황인지 구분합니다.
  • worktree로 작업 폴더를 나눠서, AI에게 병렬로 일을 시킬 준비를 합니다.
  • 혼자 MVP를 만들 때 과한 Git 규칙과 필요한 안전장치를 구분합니다.

이 레슨의 위치

  • 앞에서는 첫 커밋, GitHub 연결, push/pull의 큰 흐름을 봤습니다.
  • 이번 레슨은 Git 고급 명령을 외우는 시간이 아니라, 문제가 생겼을 때 어떤 단어로 AI에게 물어볼지 잡는 시간입니다.
  • 비개발자 입장에서는 모든 옵션을 외우기보다 "이 상황이면 reset인지, stash인지, branch인지" 정도만 구분해도 충분합니다.

gitignore

  • .gitignore는 Git에 올리지 않을 파일 목록입니다.
  • .env.local처럼 키가 들어 있는 파일, node_modules나 .next처럼 다시 만들 수 있는 폴더는 보통 올리지 않습니다.
  • GitHub에 올라간 파일은 다른 사람이 볼 수 있으므로, 비밀값을 올리는 실수는 초반에 막는 편이 좋습니다.

이미 비밀값이 GitHub에 올라갔다면 단순히 파일을 지우는 것만으로 끝나지 않을 수 있습니다. 이 경우에는 AI에게 "키를 폐기하고 새 키로 교체하는 절차"까지 같이 물어봅니다.

커밋은 작게, 자주 - 원자적 커밋

좋은 커밋은 한 가지 변경만 담습니다. 로그인 버그 수정과 지도 마커 기능을 한 커밋에 섞지 않는 식입니다. 이걸 흔히 원자적 커밋(atomic commit) 이라고 부릅니다.

작게 쪼개두면 좋은 이유는 단순합니다.

  • 문제가 생겼을 때 어느 변경이 원인인지 커밋 단위로 좁힐 수 있습니다.
  • 잘못된 변경만 골라서 되돌릴 수 있습니다. 커밋이 크면 멀쩡한 코드까지 같이 날아갑니다.
  • AI에게 "3번째 작업 전으로 돌아가서 다시 해줘"라고 시킬 수 있는 기준점이 생깁니다.

AI에게 일을 맡길 때는 하나의 작업이 끝날 때마다 커밋을 시키는 습관이 중요합니다. 커밋 전에 git diff로 무엇이 바뀌었는지 한 번 훑어보고, git log --oneline으로 커밋이 의미 단위로 쌓이고 있는지 가끔 확인해보세요. 커밋 메시지는 무엇을 왜 바꿨는지 한 줄이면 충분합니다.

P1변경을 의미 단위로 커밋시키기
지금까지 작업한 변경을 의미 단위로 나눠서 커밋해줘.

- 한 커밋에는 한 가지 변경만
- 커밋 메시지는 무엇을 왜 바꿨는지 한 줄로
- 커밋하기 전에 어떻게 나눌지 먼저 보여줘

되돌리기 - 내 상황이 셋 중 어디인지

되돌리기 명령은 여러 개지만, 내 상황이 어디인지만 구분하면 나머지는 AI에게 시키면 됩니다.

  • 아직 커밋하지 않은 변경을 버리고 싶다 → restore
  • 최근 커밋 자체를 되감고 싶다 → reset
  • 이미 GitHub에 push한 커밋을 뒤집고 싶다 → revert (기록을 지우지 않고, 반대 방향 커밋을 새로 쌓습니다)

stash는 조금 다른 도구입니다. 아직 커밋하지 않은 변경을 버리는 게 아니라 잠깐 치워두고, 깨끗한 상태로 다른 일을 본 뒤 다시 꺼내올 때 씁니다.

reset처럼 변경을 잃을 수 있는 명령은 실행 전에 AI에게 현재 git status를 보여주고 다음 명령을 확인받는 편이 안전합니다.

정말 다 날린 것 같은 순간에도 reflog라는 최후의 안전망이 있습니다. Git은 브랜치가 가리켰던 지점을 한동안 기억하고 있어서, 대부분 복구할 수 있습니다. 당황하지 말고 AI에게 "reflog로 복구해줘"라고 물어보세요.

머지 충돌을 만나면

  • 두 브랜치가 같은 파일의 같은 부분을 다르게 고쳤을 때, Git은 어느 쪽이 맞는지 스스로 정하지 않고 멈춥니다. 이게 머지 충돌입니다.
  • 파일 안에 <<<<<<< 같은 표시가 생기는데, 파일이 깨진 게 아니라 "둘 중 어느 쪽을 남길지 골라달라"는 상태입니다.
  • 충돌 파일을 AI에게 보여주고 양쪽 변경의 의도를 설명하면 대부분 잘 정리해줍니다. 중요한 건 정리된 결과가 내 의도와 맞는지 실행해서 확인하는 쪽입니다.

worktree

worktree는 같은 저장소를 여러 작업 폴더로 나눠서 쓰는 기능입니다. 폴더마다 다른 브랜치를 열어둘 수 있어서, 한쪽 폴더에서는 배포 버그를 고치고 다른 폴더에서는 새 기능을 계속 만들 수 있습니다.

바이브코딩에서 worktree가 중요한 이유가 있습니다. AI 에이전트에게 일을 시키면 그 작업 폴더는 사실상 에이전트가 점유합니다. 에이전트가 기능을 만드는 중간에 급한 수정이 생겼을 때, 같은 폴더에서 브랜치를 오가면 에이전트의 작업이 꼬입니다. 폴더를 하나 더 만드는 쪽이 안전합니다. 에이전트 여러 명에게 병렬로 일을 시키는 단계가 되면 worktree는 선택이 아니라 기본 세팅이 됩니다.

명령은 세 개만 알면 됩니다.

worktree 기본 명령
$git worktree add ../my-app-fix -b fix/urgent  # 옆 폴더에 새 브랜치로 작업 공간 만들기
$git worktree list  # 지금 열려 있는 작업 폴더 확인
$git worktree remove ../my-app-fix  # 작업이 끝난 폴더 정리

처음 쓸 때 막히는 지점 두 가지:

  • 같은 브랜치를 두 폴더에서 동시에 열 수는 없습니다. worktree를 만들 때는 보통 새 브랜치를 함께 만듭니다.
  • 새 worktree 폴더에는 node_modules와 .env.local이 없습니다. Git이 추적하지 않는 파일은 복사되지 않기 때문에, 의존성 설치와 환경변수 파일 복사를 다시 해줘야 앱이 돌아갑니다.

뒤의 런칭/운영 편과 Agentic 편에서 병렬 작업 자동화를 다룰 때 worktree를 실제로 씁니다. 그때 명령이 기억나지 않으면 이 페이지로 다시 돌아오세요.

브랜칭 전략

  • 브랜칭 전략은 "어떤 브랜치에서 작업하고, 언제 main에 합칠지"에 대한 팀 규칙입니다.
  • 회사나 팀 프로젝트에서는 main은 항상 정상 동작, 변경은 PR로 검토, 큰 변경은 작은 단위로 나누기 같은 규칙을 둡니다.
  • 혼자 MVP를 만드는 초반에는 복잡한 전략보다, 기능 단위 브랜치와 자주 커밋하는 습관이 더 중요합니다.
  • 가장 단순한 전략은 main을 기준점으로 두고, 새 기능은 별도 브랜치에서 만든 뒤 괜찮으면 합치는 방식입니다.
  • 브랜치 이름은 feature/login, fix/map-marker, chore/update-readme처럼 작업 목적이 보이면 충분합니다.
  • AI에게 큰 변경을 맡길 때는 먼저 새 브랜치를 만들고, 작업이 끝난 뒤 diff와 실행 결과를 확인한 다음 main에 합칩니다.
기능 브랜치에서 작업 시작하기
$git status  # 현재 변경이 남아 있는지 확인
$git branch  # 현재 브랜치 확인
$git switch -c feature/map-filter  # 새 기능 브랜치 만들고 이동

초반 혼자 작업에서는 전략 이름을 외우기보다, main을 안정적인 기준점으로 남기고 실험은 브랜치에서 한다는 감각이 더 중요합니다.

마무리

  • Git 고급 기능은 많이 아는 것보다, 위험한 순간에 멈추고 상태를 확인하는 감각이 더 중요합니다.
  • 혼자 만들 때는 단순하게 시작하되, .gitignore, 작은 커밋, 브랜치 분리만 지켜도 AI 작업이 훨씬 안전해집니다.
  • worktree는 지금 당장 안 써도 됩니다. 다만 병렬 작업이 시작되면 반드시 다시 만나게 되니, 위 명령 세 개의 위치만 기억해두세요.
