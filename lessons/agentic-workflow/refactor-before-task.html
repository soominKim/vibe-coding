에이전틱 워크플로우

작업 전에 검증 환경 만들기

큰 작업 전 TypeScript, lint, test 기본 환경을 갖추는 방법

얻어갈 것

  • 큰 작업을 맡기기 전에 TypeScript, lint, test를 먼저 준비합니다.

기능 구현 전에 코드베이스를 정비합니다

검증 고도화하기에서 본 기계 검증은 실행할 명령이 있어야 작동합니다.

  • 타입 체크가 없으면 구조 변경 중 생기는 값의 모양 오류를 놓칩니다.
  • lint가 없으면 사소한 코드 품질 문제가 계속 쌓입니다.
  • test가 없으면 핵심 동작을 매번 사람이 직접 확인해야 합니다.

그래서 큰 기능을 맡기기 전에, 먼저 검증 가능한 코드베이스로 정비합니다.

기본 환경 세 가지

이 레슨에서는 TypeScript의 타입 체크(type check), 린트(lint), 테스트(test)를 최소 검증 환경으로 잡습니다.

환경확인하는 것
TypeScript 타입 체크파일 사이 값의 모양과 함수 사용이 맞는지
lint코드 스타일, 위험한 패턴, 놓친 import 같은 기본 품질
test중요한 동작이 의도대로 유지되는지

타입 체크

값의 모양이 안 맞을 때 잡아줍니다.

function discountPrice(price: number) {
  return price * 0.9
}

discountPrice("만원")  // ❌ 여기는 숫자여야 하는데 글자가 왔어요
user.email            // ❌ email 이라는 값은 없어요

lint

여러 사람이 짜거나 AI가 매번 새로 짜도 코드 모양이 제각각이 되지 않게, 정해 둔 코드 컨벤션(코드 스타일 규칙)에 맞춰줍니다.

const  name='호연'   // 간격도 따옴표도 제각각
const age =32

lint를 돌리면 이렇게 통일해주고, 이런 건 상당수 자동으로 고쳐집니다.

const name = "호연"
const age = 32

test

중요한 동작이 바뀌면 알려줍니다.

test("10% 할인", () => {
  expect(discountPrice(10000)).toBe(9000)  // 이 값이 깨지면 빨간불이 뜹니다
})

처음 프로젝트를 만들 때도 가능하면 이 세 가지를 기본 환경으로 잡는 걸 추천합니다. 나중에 붙일 수도 있지만, 기능이 쌓인 뒤에는 기존 코드 정리부터 해야 해서 작업이 커집니다.

리팩토링 계획 세우기

아래 P1 프롬프트는 기능 구현이 아니라 검증 환경 정비만 맡깁니다. 범위를 이렇게 잘라야 다음 작업에서 verify나 코드리뷰가 볼 증거가 생깁니다.

P1검증 환경 먼저 갖추기
큰 기능을 만들기 전에 이 프로젝트를 검증 가능한 상태로 정비하려고 한다. 

- TypeScript 타입 체크, lint, test를 실행할 수 있게 만든다.
- 주요 js, jsx 파일은 타입스크립트 확장자(ts, tsx)로 변경하고 기본적인 타입을 적용한다.
- 기존 구현된 모든 기능과 UI는 영향이 가지 않도록 한다.
- 기능 구현이나 화면 변경은 하지 않는다.
- 끝나면 추가한 명령을 실제로 실행하고 결과를 알려준다.

먼저 현재 점검을 하고 개선 계획을 세워줘

기계 검증 자동화하기

앞의 명령을 갖췄으면, 이제 사람이 매번 챙기지 않아도 검사가 돌게 만듭니다.

  • 커밋이 원격 저장소로 올라가기 전에, 로컬에서 기계 검증을 통과해야만 넘어가게 강제할 수 있습니다.
  • 커밋 직전에 검사하는 pre-commit을 걸면, 커밋하는 순간 검사가 돌고 실패하면 커밋이 막힙니다.
  • pre-commit에는 타입 체크, lint, test를 우선 자동으로 돌게 합니다 (build는 시간이 오래 소요될 수 있어 제외합니다)
  • 나중에는 여기서 더 나아가 브랜치 → PR → CI를 거쳐 머지하는 식으로 더 안정적으로 갖춥니다.
P2커밋 전에 자동 검사 걸기
커밋할 때마다 타입 체크, lint, test가 자동으로 돌게 pre-commit을 걸어주라
