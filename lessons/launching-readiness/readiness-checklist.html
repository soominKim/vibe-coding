런칭/운영 체크리스트

런칭과 운영 체크리스트

첫 사용자 공개와 이후 운영을 위해 확인할 항목을 정리합니다.

얻어갈 것

런칭하기 전 확인할 것을 시작으로 사용자/운영자 관점, 장애 대응, 보안과 데이터 그리고 모니터링까지 질문을 확인합니다.

1. 런칭하기 전 꼭 알아두면 좋을 것

  • 링크를 공유했을 때 미리보기가 잘 보이는지 확인합니다.
  • 검색 엔진에 잘 노출될 수 있도록 기본 SEO 설정을 했는지 확인합니다.
  • 개인정보처리방침과 이용약관이 필요한 위치에 연결되어 있는지 확인합니다.
  • 브라우저 탭에 서비스 이름과 favicon이 제대로 보이는지 확인합니다.
  • 사용자가 문의하거나 도움을 받을 수 있는 경로가 보이는지 확인합니다.

이어지는 챕터: 첫 사용자가 들어오는 순간, 서비스 보안 점검하기

2. 사용자가 바로 사용할 수 있는 상태인가?

제작자의 의도에 맞게 서비스가 잘 만들어졌는지와 사용자가 실제로 사용하는 건 다른 문제입니다. 서비스를 처음 본 사람이 설명을 듣지 않아도 핵심 기능을 한 번 써볼 수 있어야 합니다.

  • 첫 화면에서 이 서비스가 무엇을 하는 곳인지 단 번에 알 수 있습니다.
  • 가장 중요한 사용 흐름을 한 번 끝까지 경험할 수 있습니다.
  • 데스크톱/모바일 모두 핵심 화면과 행동이 어색하지 않습니다.
  • 로딩 중이거나 데이터가 늦게 뜰 때도 서비스가 멈춘 것처럼 보이지 않습니다.
  • 서비스 안의 문구가 개발자용 표현이나 임시 문구처럼 보이지 않습니다.

3. 운영자가 요청과 서비스를 관리할 수 있는가?

운영자는 사용자의 제보나 수정 요청을 처리할 수 있어야 하고, 동시에 서비스가 지금 어떤 상태인지 확인할 수 있어야 합니다. 처음부터 큰 관리자 시스템이 필요한 것은 아니지만, 요청과 운영 상태를 한곳에서 보고 판단할 최소 환경은 있어야 합니다.

  • 사용자가 남긴 제보, 문의, 수정 요청이 어딘가에 남습니다.
  • 운영자가 서비스의 핵심 데이터와 상태를 확인할 수 있는 화면이나 도구가 있습니다.
  • 운영자가 새 요청, 처리 중인 요청, 끝난 요청을 구분할 수 있습니다.
  • 긴급하게 숨기거나 고쳐야 할 항목을 운영자가 직접 판단할 수 있습니다.

이어지는 챕터: 운영 화면과 탐색 개선

4. 문제가 생겼을 때 원인을 찾고 대응할 수 있는가?

네 번째 질문은 버그와 장애 대응입니다. 사용자가 "안 돼요"라고 말했을 때 어디서 막혔는지 추적할 단서가 있어야 합니다.

  • 사용자가 문제를 알려줄 CS 대응 통로가 있습니다. (이메일, 챗봇 솔루션 등)
  • 사용자가 문제를 보낸 시간, 화면, 행동을 함께 남길 수 있습니다.
  • 에러가 발생했을 때 이를 확인할 로그와 메트릭이 남아 있습니다.
  • 같은 문제가 여러 사용자에게 반복되는지 확인할 수 있습니다.
  • 외부 서비스 장애인지 우리 서비스 문제인지 구분할 단서가 있습니다.
  • 사용자가 서비스에서 어떻게 행동하는지 데이터를 확인할 수 있습니다.

이어지는 챕터: 운영 신호와 로그 점검

5. 공개하면 안 되는 것이 밖으로 나가지 않는가?

다섯 번째 질문은 보안과 공개 범위입니다. 보안은 어려운 해킹 기법부터 보는 것이 아니라, 공개 화면과 API 응답에 숨겨야 할 정보가 섞여 나가지 않는지 확인하는 데서 시작합니다.

  • 아직 보여주면 안 되는 화면이나 기능이 공개되어 있지 않습니다.
  • 내부 테스트용 문구, 더미 데이터, 임시 버튼이 남아 있지 않습니다.
  • 사용자 정보나 운영자용 정보가 다른 사용자에게 보이지 않습니다.
  • API 응답에 다른 사용자의 데이터, 운영자용 데이터, 내부 상태값이 섞여 나오지 않습니다.
  • API 키, 비밀 설정값, 내부 링크가 공개 화면이나 저장소에 드러나지 않습니다.
  • 오류 화면이 내부 정보까지 그대로 보여주지 않습니다.

6. 계속 운영할 수 있는 비용과 의존성을 알고 있는가?

여섯 번째 질문은 지속 가능성입니다. 보통 하나의 서비스를 운영할 때 외부 서비스를 자연스럽게 사용하고, 필요에 따라 비용을 지불합니다.

  • 어떤 외부 서비스에 의존하는지 알고 있습니다.
  • 사용자가 늘어났을 때 비용이 생기는 지점을 알고 있습니다.
  • 외부 서비스가 멈추거나 제한에 걸리면 서비스가 어떤 영향을 받는지 알고 있습니다.
  • 테스트 데이터와 실제 운영 데이터를 구분할 수 있습니다.
